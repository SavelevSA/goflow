# Архитектура GoFlow

Браузер загружает Go/WASM у локального сервера. Компоненты go-app получают снимок по HTTP GET и отправляют команды по HTTP POST. `net/http` направляет `/api/...` в `internal/api`, а браузерную страницу и её ресурсы отдаёт через `app.Handler`.

| Модуль | Ответственный | Работа |
|---|---|---|
| `cmd/goflow`, `internal/api`, `internal/model` | №1 | Сервер, общие типы, контракт и интеграция |
| `internal/sim` | №2 | Движение, очереди, хранение состояния и цикл симуляции |
| `internal/control`, `internal/metrics` | №3 | Фазы светофоров, статистика и сравнение режимов |
| `internal/ui`, `web/style.css` | №4 | Карта, элементы управления, статистика и HTTP-клиент |

Оба варианта программы входят через `cmd/goflow`. Браузерная сборка регистрирует компоненты и выполняется через `app.RunWhenOnBrowser`. Нативная сборка запускает HTTP-сервер с API. Build tags исключают серверные пакеты из браузерной сборки. Клиент может импортировать `internal/model` для разбора JSON.

## Контракт движка

Интерфейс `api.Simulation` задаёт методы `Snapshot`, `SetMode`, `SetDensity`, `SetPaused`, `Reset`, `Start` и `Stop`. Реализация движка неявно удовлетворяет этому интерфейсу. Предложение для №2 — одна goroutine владеет изменяемым состоянием и принимает команды через канал. Успешный возврат из команды означает, что следующее чтение состояния уже видит изменения. `Snapshot` возвращает согласованную копию, включая независимые срезы. `Start` запускает цикл в фоне, `Stop` дожидается его завершения, отмена контекста также останавливает цикл.

Предложение для согласования с №2 и №3 — контроллер получает текущую фазу, её длительность и длины двух очередей, затем возвращает фазу для следующего шага. Движок владеет длительностью фаз. Статистика считается по состоянию движка. №2 и №3 уточняют Go-сигнатуру контроллера до подключения пакетов.

День 1 использует фиксированный Snapshot. На день 2 запланирован REST API с валидацией команд, на день 3 — подключение движка и контроллеров.
